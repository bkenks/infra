# How the docker stacks work

Every Docker Compose stack is one field of a single CUE value, `stacks.<name>`. CUE renders
each stack to the `compose.yaml` in the directory of the same name. The rendered files are
committed, and Komodo deploys them from that directory. The deploy pipeline never runs CUE.

## Layers

| Layer | What |
| --- | --- |
| Compose schema | Upstream Compose JSON Schema imported as `#Compose`, plus a generated regex of valid service keys. Regenerated by a mise task, never edited by hand. |
| `#Stack` | House spec unified with `#Compose`: derived `container_name`, network and volume names, default `restart` and `logging`, hidden `_ref` handles, a closed service key set, and service networks checked against the stack's networks. |
| snippets | Shared hidden values for stacks: domains, mounts, labels, healthchecks. |
| stacks | One file per stack, each defining `stacks: <name>: S={...}`. |
| `store` | Cross-tool data (hosts, shared external networks, host paths) embedded from YAML and read by Ansible too. |

## Referencing things

- **Itself:** a service alias, e.g. `app: Svc={ _port: 8000, expose: [Svc._port] }`.
- **A sibling in the same stack:** the stack alias, e.g. `S.services.db._ref` for the
  hostname, `S.volumes.data._ref` for a mount source, `S.networks.default._ref` for a
  network.
- **Another stack:** the full path, e.g. `stacks.komodo.services.app._port`.

Fields that start with `_` are hidden. They never reach the rendered YAML, so a stack can
carry ports, endpoints, and helper values beside its Compose fields.

## Workflow

1. Edit a stack's CUE file.
2. Run `mise run cue:vet` from the repo root.
3. Run `mise run cue:render` from this directory. It writes every `compose.yaml` and
   checks each one with `docker compose config`.

The pre-commit hook runs both steps and stages the rendered files.

Commands: `mise tasks`. Decisions: `logs/ADRs/`.
